# 分镜审核台 · 版本与发布规范

## 1. 版本规则

- 正式版本统一使用无缓存后缀的语义版本：`X.Y.Z`，例如 `0.1.12`。
- Git 标签在版本前加 `v`：`v0.1.12`。
- 产品页面、`package.json`、健康接口、个人插件清单、MCP 服务、安装器、启动器、使用说明和安装包目录必须显示同一个正式版本。
- `0.1.12+cache1`、日期后缀或临时构建号只允许用于未公开的调试缓存，不得出现在正式安装包、插件清单或公开 Release。
- `package.json` 是发布时的版本源；构建前用自动校验确认其他位置与它一致。

版本含义：

- `Z`：兼容修复、小优化、安装包或文档随代码同步更新。
- `Y`：增加可见能力或改变工作流，但保持用户数据可迁移。
- `X`：存在不兼容的数据或工作流变化，需要单独迁移方案。

## 2. 交付物命名

本地构建文件保留中文产品名：

```text
分镜审核台-vX.Y.Z-Windows.zip
分镜审核台-vX.Y.Z-Windows.zip.sha256.txt
分镜审核台-vX.Y.Z-macOS-universal.zip
分镜审核台-vX.Y.Z-macOS-universal.zip.sha256.txt
```

GitHub Release 使用稳定英文文件名，避免不同下载渠道处理中文名时产生歧义：

```text
storyboard-review-desk-vX.Y.Z-Windows.zip
storyboard-review-desk-vX.Y.Z-Windows.zip.sha256.txt
storyboard-review-desk-vX.Y.Z-macOS-universal.zip
storyboard-review-desk-vX.Y.Z-macOS-universal.zip.sha256.txt
```

ZIP 解压后的根目录可以使用中文名称，但同一版本不得出现多个内容不同、名称相同的安装包。

## 4. 插件升级规则

- 一键安装不是在线自动更新；它安装当前工具包内携带的插件版本。
- 用户换用新版本时，应关闭旧审核台服务和 Codex，完整解压新包，迁移或恢复旧数据，再运行新包的一键安装。
- 一键安装必须覆盖个人插件源码、个人市场登记和插件缓存，随后用户重启 Codex 并新建一个本地工作任务验证新版本。
- 工具包目录移动或改名后，必须重新一键安装，避免缓存入口继续指向旧目录。
- 旧版本仍占用 `43127` 时，新启动器必须停止并明确提示，不得悄悄打开旧页面。

## 5. 发布前检查

1. 更新 `package.json`，同步页面、健康接口、插件、MCP、安装器和文档版本。
2. 运行完整自动测试和插件校验；生成 Windows/macOS 包后再跑安装包级回归。
3. 在干净 Windows 和 Mac 上按双平台矩阵完成真机验收；未完成项必须在 Release 说明中标记。
4. 计算 ZIP SHA256，并验证摘要文件中的文件名和实际公开名称一致。
5. 核对安装包不含 `data/project.json`、用户资产、宫格版本、日志、备份、令牌或临时测试文件。
6. 更新 README、安装说明、测试用例、迭代计划和里程碑记录。
7. 用户明确下达“发布到 GitHub”后，才推送源码、创建不可移动标签并上传 Release 文件。
8. 发布后重新下载公开文件，核对大小和 SHA256，再把 Release 设为学员下载入口。

## 6. 回滚与修复

- 已发布标签和资产保持不可变；发现问题时发布 `Z + 1`，不覆盖旧包。
- P0 安装或数据问题应暂停旧版分发，在 README 和 Release 中给出影响范围、临时规避和新版链接。
- 用户数据升级前先导出备份；迁移失败时保留旧数据，不自动删除或覆盖。
- 仅文档纠偏且不改变安装包时可以提交到主分支，但必须写清标签提交与文档提交的差异。
